## 0. 设计前提与勘察结论（**决定本特性形状的四条硬事实**）

### 0.1 外置资料当前**结构性不可见**（不是「忘了接」，是架构上就没通道）

勘察结论（读 `electron/workspaceBackup/manifest.ts` 全文）：

- `buildManifest(root, limits, overrides)` 唯一入参是**空间根 `root`**（`manifest.ts:235`），
  其 `walk()` 从 `root` 起**只向下递归**（`manifest.ts:222` `await visit(root, '')`）。
- **没有任何字段能表达「在 root 之外、但应纳入本次备份的额外条目」**。
  `ManifestOverrides`（`manifest.ts:71`）只有 `replacement`（替换既有条目的内容源）与 `omit`（剔除既有条目），
  **两者都只能作用于已经在 root 内的路径**。
- 结论：一份位于 `D:\文献\某论文.pdf`、而空间在 `C:\Users\...\.mimir\spaces\<id>` 的资料，
  今天**无论用户怎么操作都不会进归档**。待办 4 要补的正是这条通道。

**→ 设计含义**：待办 4 **不是 UI 特性，是 manifest/packer 的扩展**。UI 只是入口。

### 0.2 「打包时临时选择」被否决（**这是本稿最重要的裁决**）

直觉方案是「打包时弹一个文件选择器让用户勾外置文件」。**否决**，三条理由：

1. **违背 I6 的「离线维护窗口」前提**（计划「固定边界」第 1 条：进维护 → 保存 → 关闭日常窗口）。
   维护模式是一个**无人值守的收尾流程**；在其中弹模态选择器，等于要求用户守在屏幕前，
   把「后台维护」变回「交互向导」。批次 4 自检 / 批次 5 保留策略都是**先预览再确认**式，
   **没有一处在打包中途要用户输入**。
2. **不可复现**：同一空间两次备份若每次都靠现场勾选，归档内容随勾选手势漂移，
   `verify` 的「清单 vs 归档一一对应」虽仍自洽，但**跨次可比性丧失**——而 I6 全篇的验证口径
   都建立在「同一空间多次生成清单结果可复现」（`manifest.ts:193` 排序注释）之上。
3. **与「登记」二字直接冲突**：计划原文用的是「**显式选入登记**」——`登记`（register）是
   **一次性的、持久的**动作；`选择`（select）若是每次都做，就不该叫登记。中文措辞本身排除了临时勾选。

**→ 裁决**：实现为 **登记表（registry）**——用户在**日常模式**下把外置资料「登记」进空间，
备份时**只读地把登记表并进清单**，维护流程仍是无人值守的。

### 0.3 「未包含依赖明确报告」已有承载点，登记特性必须复用它

`manifest.ts:79` 的注释把 `ExcludedEntry` 的用途写得极清楚：

> 「未纳入备份的条目（供上层向用户"明确报告"，对应 INTEGRATION-PLAN-I6『未包含依赖明确报告』）」

当前 `reason` 只有 `'oversize'`（`manifest.ts:88`）。登记特性的「**用户登记了、但登记当时源文件已不在**」
这类情形，**天然属于同一个报告通道**，只需扩展 `reason` 联合类型，
**不再造第二个报告机制**（对齐「不给基础设施加第二套真相」的既有纪律）。

### 0.4 登记必须**复用 `pickedPaths` 授权门**，不得新开旁路

`electron/ipc/rendererPathGuards.ts:154` 的 `assertRendererFilePath` 是渲染层读盘的**唯一**授权门，
`pickedPaths`（`:21`）由 `dialog:open` 成功回调填充（`electron/ipc/index.ts:266`）。
登记外置资料 = 渲染层要把**空间外**的绝对路径持久化，这是**当前权限模型下最敏感的一类操作**
（比读单个文件更敏感：它把「一次性选中」升级成「长期记住」）。

**→ 设计含义**：登记入口**必须**经原生对话框（进 `pickedPaths`），
登记表落盘的**只能是**被 `assertRendererFilePath` 放行过的路径；
**绝不允许**渲染层直接提交任意路径字符串。§4.2 给出这条约束的具体落地。

## 1. 特性定义（本稿裁决的形态）

### 1.1 一句话

**在空间内维护一张「外置资料登记表」，记录用户显式选入的空间外文件/目录；
备份时按登记表把仍在原地的条目并入归档，并对「登记了但已不可用」的条目出明确报告。**

### 1.2 范围边界（**做什么 / 不做什么**，逐条对齐计划原文）

| 项 | 裁决 | 依据 |
|---|---|---|
| 外置**文件**（PDF 等） | **纳入** | 计划逐字「外置 PDF」 |
| 外置**目录**（项目根） | **纳入**（递归，且**沿用 manifest 的全套防御**） | 计划逐字「项目」 |
| **聊天产物**（本空间 produce 出的、但落在空间外的文件） | **纳入**（与前者同机制） | 计划逐字「聊天产物」 |
| 全局凭据 / 模型配置 / 服务器配置 | **永不纳入** | 计划边界逐字排除 |
| 安装目录 / Chromium 缓存 | **永不纳入** | 计划边界逐字排除 |
| **符号链接 / 联接** | **仍拒绝**（不因「用户显式登记」而放宽） | §2.2 |
| 网络路径 / 映射盘 | **仍拒绝** | 计划边界「网络路径……均阻断」 |
| 外置资料**内容**本身 | **不复制进空间**，只登记**引用** | §2.3 |

### 1.3 与非目标的区分（避免范围蔓延）

- **不做**「自动发现外置资料」（如全盘扫描 PDF）——计划要求「**显式**选择」，自动发现直接违背。
- **不做**「外置资料的版本管理」——那是资产库（`electron/assets/`）的职责，登记表只记**引用**。
- **不做**「跨空间的资料共享表」——登记表**属于某个空间**，随空间迁移/恢复一并走。

## 2. 数据模型

### 2.1 登记表落点：**空间内**、随备份走

**裁决**：登记表落 `<space>/.mimir/external-registry.json`（**空间根内**，正斜杠语义）。

理由：
- **必须随空间迁移/恢复**——用户登记的外置资料属于这个科研空间的知识边界，
  恢复为新空间时应当原样带走（这正是 `manifest.ts` 会把 `.mimir/` 下非排除内容打进归档的原因）。
- **与 `.mimir/assets/staging/` 不同**：那是过程产物（`manifest.ts:104` 排除），
  登记表是**稳定内容**，不该被排除。
- **不落 `~/.mimir/`（home 级）**：那会让「换空间」丢失登记，
  且 home 级是凭据类数据的地盘（`registryView.ts` / `registryAppend.ts`），语义冲突。

> ⚠️ **与批次 3 恢复路径重写的关系**：登记表内若存**绝对路径**，
> 恢复为新空间（路径变化）后这些引用会失效。§4.4 给出「路径重写 vs 失效报告」的裁决。

### 2.2 登记条目形状（草案）

```jsonc
// <space>/.mimir/external-registry.json
{
  "version": 1,
  "entries": [
    {
      "id": "ext-1750000000000-a1b2c",   // 稳定标识（UI 增删改查的键）
      "path": "D:/文献/某某研究.pdf",     // 绝对路径（正斜杠）——登记当时经 picker 授权
      "kind": "file",                     // file | directory
      "label": "某某研究.pdf",            // 展示名（用户可改；默认取 basename）
      "addedAt": "2026-10-12T07:00:00.000Z",
      "addedBy": "user"                   // 预留：未来可能有 chat/produce 自动登记入口
    }
  ]
}
```

字段裁决要点：
- **`kind` 显式记录**：目录需递归（沿用 `walk()`），文件不递归。**不在打包时用 `stat` 猜**——
  登记当时与打包当时之间目录可能被替换为文件（见 §5.1 的 TOCTOU 讨论）。
- **`path` 用正斜杠**：与 `manifest.ts:13` 「路径全部用正斜杠」一致，跨平台解释统一。
- **`label` 与 `path` 分离**：`path` 是可验证的真相，`label` 是纯展示；改名不影响引用。
- **`version` 从 1 起**：给未来的格式演进留出口（对齐 `registryView` 的版本字段惯例）。

### 2.3 存引用不存内容（**关键裁决**）

登记表**只记路径**，外置资料的字节**不复制进空间**。理由：

1. **空间体积**：把 20 GB 的项目目录复制进空间，会让每次备份都膨胀 20 GB，
   而 I6 保留策略默认留 **20 份**（批次 5）→ 400 GB。**不可接受**。
2. **语义**：用户登记的是「这份资料属于我的科研空间」，**不是**「把这份资料搬进空间」——
   后者是「导入资产」（`assets:importFile`，`electron/ipc/assets.ts`）的职责，两者必须分开。
3. **备份时读源**：`createBackup` 已是流式读源（`manifest.ts:151` `hashFile` 流式 + ZIP64），
   从空间外路径流式读**在机制上无差别**——只是清单里多几条 `path` 前缀不同的条目。

**代价（必须记录，不隐瞒）**：登记表**不防源文件被删/改**。用户在登记后删掉 `D:/文献/x.pdf`，
下次备份时该条目**必然**不可用 → 走 §3.3 的「明确报告」。**这是设计取舍，不是缺陷**：
「登记」保的是「用户表达的意图」，不是「资料的不变性」；后者的正确工具是「导入资产」。

## 3. 与备份/验包链路的衔接

### 3.1 打包时的并入点（**唯一扩展点**）

批次 2 的链路是：`backupService.runSpaceBackup` → `packer.createBackup` → `buildManifest`.

**裁决**：扩展 `buildManifest` 新增可选参数 `external?: ExternalManifestInput[]`，
由 `backupService` 从**登记表**读出后传入。**不新建打包路径**。

```
runSpaceBackup(deps)
  ├─ 读 <space>/.mimir/external-registry.json      ← 新增（只读；文件不存在 = 空登记）
  ├─ buildManifest(root, limits, overrides, external)  ← 新增第 4 参
  └─ 其余不变
```

### 3.2 外置条目在清单里怎么表示（**决定 verify 是否要改的核心问题**）

清单条目 `ManifestEntry.path` 当前是「**相对空间根**的正斜杠路径」（`manifest.ts:26`）。
外置条目**无法表达成 root 的相对路径**（它在 root 外）。

**两个候选**：

| 方案 | 表示 | 优点 | 缺点 |
|---|---|---|---|
| **A. 归档内虚拟根** | `path = "__external__/ext-<id>/<原文件名>"` | 清单/zip 不变形；`verify` **零改动** | 归档内路径是合成的，需额外映射回真实源 |
| **B. 真实绝对路径** | `path = "D:/文献/x.pdf"` | 直观 | 破坏「路径必须相对 root」不变式；`validateArchivePaths` 可能误判 |

**裁决：方案 A**。理由：

1. **`verify.ts` 零改动**是压倒性优势——验包是安全关键路径（逐文件 SHA256），
   不动它就不引入新风险。
2. `validateArchivePaths`（`manifest.ts:242`）的 Windows 保留名/大小写冲突检查**继续适用**
   （因为归档内路径仍是「相对虚拟根」的相对路径）。
3. 用 `ext-<id>`（登记条目的稳定 `id`）而非原文件名做目录段，**天然消除同名冲突**
   （两个不同目录下的 `x.pdf` 不会撞车）。
4. 归档内**必然带原始文件名**（`<原文件名>` 段）→ 恢复时人能看懂这是什么。

**代价**：需要在归档里额外存一份「虚拟路径 ↔ 真实源路径」的映射，恢复时才能还原。
**裁决**：映射写进 `ArchiveManifest`（批次 3 已有的清单结构），作为可选字段——
**不读它则退化**（早期归档无此字段，`verify` 不依赖它，向后兼容）。§3.4 详述。

### 3.3 「登记了但已不可用」的明确报告（复用 `ExcludedEntry`）

打包时对每条登记条目做可用性检查，**不可用则进 `excluded`**（扩展 `reason`）：

```ts
export interface ExcludedEntry {
  path: string
  reason: 'oversize' | 'missing' | 'now-link' | 'rejected'   // ← 扩展
  size: number
  defaultDisposition: 'exclude'
}
```

| `reason` | 触发条件 | 用户看到的话术 |
|---|---|---|
| `missing` | `lstatSync` 抛 `ENOENT` | 「登记的资料已不在原位置」 |
| `now-link` | 原件现已是符号链接/联接 | 「登记的资料现为链接，出于安全不纳入」 |
| `rejected` | 现落在控制面/受管资产路径内（可能被别的机制移动） | 「登记的资料现位于受保护区域」 |
| `oversize` | 超 `maxFileBytes`（复用既有） | 「登记的资料超过单文件上限」 |

**这四种都「不 throw」**——与 `oversize` 同口径（`manifest.ts:207` 的可用性取舍：
「用一个 50GB 文件让整个备份永久失败，是把可用性问题当成正确性问题处理」）。
**但必须进 `excluded`**，绝静默丢弃（这是计划「未包含依赖**明确报告**」的字面要求）。

### 3.4 归档内清单（`ArchiveManifest`）的新增字段

```jsonc
// 归档内 .mimir-archive-manifest.json（批次 3 已有）
{
  "version": 1,
  "sourceRoot": "C:/Users/.../spaces/<id>",     // 批次 3 已有（绝对根，供恢复重映射）
  "external": [                                  // ← 新增（可选）
    { "virtual": "__external__/ext-abc/x.pdf", "label": "x.pdf" }
  ]
}
```

裁决：
- **只存虚拟路径 + label，不存真实源绝对路径**。理由：归档可能被拷到别的机器，
  真实源路径在那台机器上无意义且属隐私；恢复时外置资料**本就不还原**（见 §4.4）。
- 该字段**纯增量**：旧归档无之，`readArchiveManifest` 读不到即返回 `undefined`，
  恢复路径**退化**为「无外置条目」——**绝不猜测**（对齐批次 3「缺失则退化不改写」纪律）。

## 4. 入口与授权（**复用既有安全设施，不开旁路**）

### 4.1 登记动作的 API 形状

沿用 I6 的「主进程持有真相、渲染层只发意图」范式（对齐 `ASSETS_CHANNELS` / `backupSpace`）：

```
登记：renderer → ipc `external:register` { spaceId, path, kind, label }
列出：renderer → ipc `external:list`     { spaceId } → 条目数组（不含???）
删除：renderer → ipc `external:remove`   { spaceId, entryId }
```

> 命名对齐：现有通道用 `domain:verb`（`assets:*` / `figures:*` / `permissions:*`），
> 故用 `external:*` 而非 `registry:*`（后者的语义已被空间注册表 `registryView` 占用）。

### 4.2 授权链（**本特性最关键的安全约束**）

```
渲染层用户点击「登记外置资料」
  → showOpenDialog({ properties:['openFile'|'openDirectory'] })   ← 必须走这里
  → 主进程 dialog:open 回调把选中路径写入 pickedPaths             ← 既有机制，electron/ipc/index.ts:266
  → 渲染层拿 result.filePaths → 调 external:register
  → 主进程 external:register **必须** assertRendererFilePath(path) ← 复用授权门
  → 通过后才写入 <space>/.mimir/external-registry.json
```

**三条不可协商的红线**：

1. **`external:register` 必须调 `assertRendererFilePath(input, 'read')`**——
   与 `fs:readFile` 完全同一道门（`electron/ipc/index.ts:324`）。
   **未进 `pickedPaths` 的路径一律拒绝**，即便它「看起来是合法文件路径」。
2. **写入目标必须是当前空间内的登记表**（`assertRendererFilePath(..., 'write')` 同款约束，
   `rendererPathGuards.ts:163`「写入目标必须位于当前科研空间内」）。
   渲染层**无法**指定登记表落点。
3. **`spaceId` 必填且经注册表解析**（对齐 `runSpaceBackup` 的「只传 id，绝不信路径」，
   `backupService.ts:15`）。渲染层无法往任意空间写登记表。

### 4.3 登记时的即时校验（**拒绝在入口，而非在打包时**）

登记动作应当**立刻**验证：
- 路径存在（`lstatSync` 能 stat）；
- 不是符号链接/联接（`manifest.ts:180` 同款判据）；
- 不在控制面/受管资产路径内（`isControlPlanePath` / `isManagedAssetPath`，
  `rendererPathGuards.ts:157-158` 同款）；
- 在网络路径/不可用卷上（复用批次 1 的卷类型判定 `localDisk.ts`，**登记即拒**）。

**理由**：把「不可用」挡在登记时，用户能立刻得到反馈并重选；
若拖到打包时才发现，维护流程已启动，用户看到的只是一条 `excluded` 报告，体验差且难补救。
**但打包时仍要重查**——登记与打包之间有时间差（TOCTOU，§5.1）。

### 4.4 恢复语义（**裁决：外置资料不还原，只报失效**）

批次 3 恢复为**新空间**（新路径）。登记表里的绝对路径在恢复后有两种命运：

| 情形 | 处置 |
|---|---|
| 源路径在新机器上**仍存在** | 保留登记（重启后仍可用） |
| 源路径在新机器上**不存在** | 保留登记条目，但**在恢复报告里列为「待重新定位」** |

**裁决：不重写路径、不删除条目**。理由：
- **不重写**：路径重写（批次 3 的 `remapRules`）是为**空间内**路径设计的
  （旧根 → 新根的前缀替换）；外置路径与空间根无前缀关系，**没有可靠的映射规则**，
  硬套会误改。**绝不猜测**（对齐 `restoreArchive.ts` 既有纪律）。
- **不删除**：用户登记的是**意图**；源路径失效不该理解为「用户不要这份资料了」。
  保留条目 + 报告失效，让用户在新空间里手动重新定位（重登一次即可）。
- **恢复报告**复用语料：恢复结果里增一类 notice（对齐批次 4 已作 notice 上报 `staging` 残留的范式）。

## 5. 风险与未决点（**诚实列出，不粉饰**）

### 5.1 TOCTOU：登记与打包之间的时间差

登记校验（§4.3）与打包读源之间有**任意长**的时间差。期间源文件可能：
被删（→ `missing`）、被换成链接（→ `now-link`）、被移进空间（→ `rejected`）、
内容被改（→ **摘要与登记时不一致，但清单按**打包当时**算，故 verify 仍自洽**）。

裁决：**接受**。业务上「登记的内容后来变了」是正常科研行为（改稿），
备份应备份**当时**的样子（这才是备份）。**只对「不可用」报告，不尝试锁定内容**。

### 5.2 外置目录递归的上限

外置目录（项目根）可能极大/极深。**裁决**：**沿用 `buildManifest` 的全套上限**
（`maxEntries` / `maxManifestBytes` / `maxTotalBytes` / `maxFileBytes`，`manifest.ts:96`），
外置条目与空间内条目**共享同一个预算**。理由：不共享会有「用外置目录绕过上限」的漏洞。
超限的处置与空间内一致（单文件排除 / 总量超限失败）。

### 5.3 外置路径的隐私

登记表存**本机绝对路径**（`D:/文献/...`），落**空间内**、进而**进归档**。
裁决：
- **归档的清单里不存真实外置路径**（§3.4 只存虚拟路径 + label）——避免归档外泄本机目录结构。
- **空间内的登记表存真实路径**——它在空间内，本就只有本机用户可见；
  且不外泄（备份清单已剔除），符合「不写正文/凭据」（批次 4 审计纪律）。

### 5.4 未决点（**留待实施批次或用户裁决**）

1. **聊天产物如何登记**：是「用户手动登记」还是「聊天产出时自动登记」？
   `addedBy` 字段（§2.2）已预留，但**自动登记入口未定稿**——
   本稿只定**手动登记**，自动登记留待后续（涉及「哪些产物值得记」的产品判断）。
2. **登记上限**：单个空间最多登记多少条？本稿**不设硬上限**（条目数已由 manifest 上限兜底）。
3. **登记表的 UI 位置**：放「设置 → 空间」还是「资产 → 外置资料」？属产品决策，本稿不裁。
